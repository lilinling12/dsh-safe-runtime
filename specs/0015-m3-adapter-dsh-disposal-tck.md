# Spec 0015: M3 Adapter DSH Disposal Shared TCK

Status: DRAFT  
Milestone: M3-016  
Profile: `ADAPTER_DSH`

## 1. Purpose

M3-016 defines a language-independent Shared TCK contract for explicit disposal
of Adapter-owned registrations and observation subscriptions.

The contract separates four concerns that MUST NOT be collapsed into one boolean
"disposed" flag:

1. resource ownership — what the Adapter registration owns and therefore may
   unregister or close;
2. cutoff — the explicit point after which that registration MUST accept no new
   work/effect;
3. drain — whether work accepted before cutoff must settle before disposal is
   complete;
4. completion — the point at which the disposal call has fulfilled the portable
   guarantee for that resource kind.

DeepSeek Harness remains compatibility evidence only. Concrete Harness listener,
service, effect, scope, or disposer objects are not portable protocol data.

## 2. Authority and ownership boundary

A conforming Adapter MUST dispose only resources owned by the returned
registration/subscription handle.

Disposing an Adapter-owned handle MUST NOT, merely by virtue of that handle:

- dispose the caller-owned Harness `Context`;
- stop or uninstall Harness services such as SessionStore, ToolRuntime, or
  ApprovalService;
- unregister caller-owned tool definitions;
- destroy live agents or sessions;
- delete, rewrite, reorder, or retroactively reinterpret durable events already
  committed before disposal;
- imply process termination, garbage collection, replay truncation, or durable
  storage cleanup.

M3-016 proves registration/subscription lifecycle only. Runtime/service teardown
outside the returned handle remains externally owned.

## 3. Operation

The M3-016 portable operation is:

```text
disposal
```

Every fixture uses profile `ADAPTER_DSH` and exactly one disposal resource kind.

## 4. Resource kinds

M3-016 recognizes exactly these portable resource kinds:

```text
OBSERVATION_SUBSCRIPTION
TOOL_POLICY_REGISTRATION
MONOTONIC_TOOL_GUARD_REGISTRATION
TURN_STOPPING_REGISTRATION
```

Unknown resource kinds fail fixture validation.

The profile does not assert that every implementation exposes these handles with
the same concrete API shape. The portable requirement is the observable lifecycle
contract described below.

## 5. Observation subscription contract

### 5.1 Source fact

Portable source form:

```json
{
  "kind": "OBSERVATION_SUBSCRIPTION",
  "acceptedBeforeDispose": ["before-1"],
  "probedAfterDispose": ["after-1"],
  "repeatDispose": true
}
```

The identifiers are deterministic probe references, not Harness event ids.

### 5.2 Required semantics

For `OBSERVATION_SUBSCRIPTION`:

1. events/work accepted by the subscription before the disposal cutoff remain
   owned by that subscription;
2. the disposal call establishes a cutoff after which the subscription accepts
   no new observation delivery work;
3. disposal completion MUST wait for already accepted observation delivery work
   to settle;
4. after disposal completion, a positive-control source event generated through
   the same still-live external runtime MUST NOT be delivered to the disposed
   subscription;
5. repeated disposal is idempotent for the M3-016 observation profile: a second
   disposal call completes without reactivating delivery or duplicating already
   accepted work;
6. `drain()` after disposal may be used to observe already-settled completion but
   MUST NOT reactivate the subscription;
7. durable source evidence generated by the external runtime after disposal may
   still exist in that runtime; lack of observer delivery does not mean the
   durable source event was deleted.

Portable observable:

```json
{
  "kind": "DISPOSAL_COMPLETED",
  "resourceKind": "OBSERVATION_SUBSCRIPTION",
  "acceptedBeforeDisposeSettled": ["before-1"],
  "effectsAfterDispose": [],
  "repeatDispose": "IDEMPOTENT",
  "externalRuntime": "REMAINS_LIVE"
}
```

## 6. Tool policy registration contract

### 6.1 Source fact

```json
{
  "kind": "TOOL_POLICY_REGISTRATION",
  "effectBeforeDispose": "DENY",
  "probeAfterDispose": "EXECUTE"
}
```

### 6.2 Required semantics

A tool-policy registration MUST be proven active before disposal with a positive
control. After its explicit disposal completes, a later execution probe MUST no
longer receive that registration's policy effect.

The portable profile does not claim that the later execution must succeed under
all circumstances; other independent policies/guards/runtime failures may still
block it. The TCK therefore requires an isolated fixture environment in which the
registered policy is the only changing blocker.

The prior denied result remains prior evidence and MUST NOT be rewritten after
registration disposal.

Portable observable:

```json
{
  "kind": "DISPOSAL_COMPLETED",
  "resourceKind": "TOOL_POLICY_REGISTRATION",
  "effectBeforeDispose": "OBSERVED",
  "effectAfterDispose": "ABSENT",
  "externalRuntime": "REMAINS_LIVE"
}
```

M3-016 requires one explicit disposal for this resource kind. Repeat-dispose
idempotence is NOT a portable guarantee unless separately standardized by a
later normative revision.

## 7. Monotonic tool guard registration contract

### 7.1 Source fact

```json
{
  "kind": "MONOTONIC_TOOL_GUARD_REGISTRATION",
  "effectBeforeDispose": "DENY",
  "probeAfterDispose": "EXECUTE"
}
```

### 7.2 Required semantics

A monotonic guard registration MUST be proven active before disposal. After the
returned registration is explicitly disposed, the exact registered guard MUST no
longer participate in future tool execution decisions.

Disposal MUST NOT be interpreted as weakening any different guard still
registered in the runtime. The portable fixture therefore isolates the guard
under test.

The prior denied result remains immutable evidence.

Portable observable:

```json
{
  "kind": "DISPOSAL_COMPLETED",
  "resourceKind": "MONOTONIC_TOOL_GUARD_REGISTRATION",
  "effectBeforeDispose": "OBSERVED",
  "effectAfterDispose": "ABSENT",
  "externalRuntime": "REMAINS_LIVE"
}
```

Repeat-dispose idempotence is not standardized for this resource kind in M3-016.

## 8. Turn-stopping registration contract

### 8.1 Source fact

```json
{
  "kind": "TURN_STOPPING_REGISTRATION",
  "effectBeforeDispose": "HANDLER_INVOKED",
  "probeAfterDispose": "TURN_STOPPING"
}
```

### 8.2 Required semantics

A turn-stopping registration MUST be proven active before disposal through an
explicit boundary invocation. Once disposal completes, a later turn-stopping
boundary in the same still-live external runtime MUST NOT invoke that disposed
handler.

Disposal of the registration MUST NOT stop the underlying agent/runtime turn
machinery and MUST NOT imply that no other independent turn-stopping handler may
run.

Portable observable:

```json
{
  "kind": "DISPOSAL_COMPLETED",
  "resourceKind": "TURN_STOPPING_REGISTRATION",
  "effectBeforeDispose": "OBSERVED",
  "effectAfterDispose": "ABSENT",
  "externalRuntime": "REMAINS_LIVE"
}
```

Repeat-dispose idempotence is not standardized for this resource kind in M3-016.

## 9. Explicit completion requirement

Absence of a later effect is not, by itself, disposal evidence.

Every conforming case MUST contain all of the following:

1. a positive-control effect proving the registration/subscription was active;
2. an explicit disposal invocation;
3. disposal completion according to the resource contract;
4. a post-disposal positive-control source probe through the same still-live
   external runtime;
5. an observable proving the disposed registration no longer contributes its
   effect.

Timing delays, garbage collection, process exit, missing source probes, or
missing results MUST NOT be used as disposal authority.

## 10. Cutoff and in-flight work

Observation delivery has an explicit drain contract in M3-016. Work accepted
before cutoff MUST settle before observation disposal resolves.

For policy, guard, and turn-stopping registrations, M3-016 standardizes removal
from future participation after disposal completion. It does NOT define forced
cancellation of a callback that had already begun before disposal was invoked.
Such in-flight callback cancellation/quiescence semantics require separate
normative authority and MUST NOT be inferred here.

This distinction prevents disposal from being misrepresented as a hard kill.

## 11. Portable fixture shape

The portable stimulus contains:

```text
operation
request
sourceFact
```

`request` contains:

```text
sessionRef
resourceRef
```

`resourceRef` is fixture-local opaque correlation data. A portable consumer may
compare it for equality but MUST NOT parse implementation identity from it.

`sourceFact` is exactly one closed resource-kind form from sections 5–8.
Unknown fields fail fixture validation.

## 12. Runner semantics

The generic Shared TCK runner preserves foundation statuses:

```text
PASS
FAIL
ERROR
```

For M3-016:

- malformed or contradictory fixture data -> fixture validation error;
- implementation throws -> `ERROR`;
- implementation returns a malformed projection -> `ERROR`;
- valid projection differs from the expected observable -> `FAIL`;
- exact match -> `PASS`.

Expectation data is comparison-only. The runner MUST NOT use `expect` to decide
which resource was disposed or which before/after effects occurred.

## 13. Required portable cases

M3-016 MUST register at least these cases:

1. observation disposal drains one already accepted asynchronous delivery,
   rejects future delivery to that subscription, tolerates repeated disposal,
   and leaves the external runtime live;
2. tool-policy disposal removes the isolated policy from a later execution while
   preserving the prior denied result;
3. monotonic-guard disposal removes the exact isolated guard from a later
   execution while preserving the prior denied result;
4. turn-stopping disposal prevents a later boundary from invoking that exact
   handler while leaving the external runtime live.

Boundary tests MUST additionally prove that:

- unknown resource kinds fail closed;
- resource-specific fields cannot be supplied to the wrong resource kind;
- observation is the only M3-016 resource kind that may claim
  `repeatDispose: true` / `IDEMPOTENT`;
- missing positive-control-before, explicit disposal completion, or
  post-disposal source probe cannot masquerade as disposal proof;
- future-effect absence cannot be manufactured from expectation data;
- malformed/non-portable values, decorated/sparse arrays, exotic objects, and
  cycles fail validation;
- implementation exceptions and malformed projections produce runner `ERROR`;
- valid mismatches produce runner `FAIL`.

## 14. Exact pinned rc5 conformance

Exact source-conformance against the accepted Harness baseline
`0.1.0-rc.5` / `47f943859bef60e4160492346772ded9b24f765a`
MUST use public seams only.

The exact proof MUST cover:

1. production `observe()` accepts evidence before disposal, unregisters its
   Harness listeners at cutoff, drains already accepted asynchronous sink work
   before disposal resolves, tolerates repeated disposal, and observes no later
   source event from the still-live runtime;
2. production `registerToolPolicy()` is active before disposal and no longer
   affects a later isolated real ToolRuntime execution after its returned
   disposer completes;
3. production `registerMonotonicToolGuard()` is active before disposal and no
   longer affects a later isolated real ToolRuntime execution after disposal;
4. production `registerTurnStopping()` is active before disposal and its exact
   handler is absent from a later real/public Harness turn-stopping boundary;
5. public Harness registration/disposer seams are used directly; private
   listener collections, private scope layers, implementation-only counters,
   garbage collection, sleeps, or process exit are not disposal evidence;
6. the external Harness context/services remain usable after each Adapter-owned
   handle is disposed.

Pinned-source documentation for `ToolRuntime.guard()` may support compatibility
claims about its returned exact guard disposer, but the portable contract remains
this Spec rather than Harness implementation prose.

## 15. Production-change rule

Existing M2 conformance already proves part of the observation and policy
disposal behavior. M3-016 MUST extend proof before changing production code.

Production Adapter changes are allowed only if the portable contract plus exact
public pinned-runtime evidence exposes a real correctness gap. Tests MUST NOT be
made green by weakening disposal completion, removing drain guarantees, widening
resource ownership, or silently swallowing lifecycle failures.

## 16. Deferred behavior

M3-016 deliberately does not define:

- replay/live reconciliation or crash-tail recovery (M3-017);
- capability lease/revocation semantics (M4);
- workspace transaction commit/rollback/disposal (M6);
- hard cancellation of callbacks already in flight when disposal begins;
- process/service/context shutdown;
- garbage-collection guarantees;
- deletion or compaction of durable evidence;
- repeat-dispose semantics for policy, guard, or turn-stopping registrations.

## 17. Acceptance criteria

M3-016 is complete only when:

- this language-independent contract exists before new TypeScript TCK
  implementation;
- required portable fixtures are registered;
- `@dsh-safe/testkit` provides strict Harness-independent parse/run projection;
- boundary tests prove resource-kind separation, positive-control requirements,
  explicit completion, and expectation/oracle independence;
- production Adapter disposal behavior is exercised directly;
- exact pinned rc5 source-conformance proves real lifecycle cutoff through public
  seams while the external runtime remains live;
- normal CI and exact pinned rc5 source-conformance are green on the exact
  implementation head;
- TypeScript strictness, schemas, validators, compatibility baseline, frozen
  lockfile, architecture/security gates, and security claims remain unchanged or
  stronger.
